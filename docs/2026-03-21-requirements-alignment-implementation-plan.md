# Skill/MCP 系统需求对齐实施计划

> 文档日期：2026-03-21
> 目标：让当前系统与题目要求对齐，可作为后续开发执行清单直接落地。

## 1. 背景与目标

当前系统已经完成了 Skill/MCP 资源、用户、组织、申请、授权等核心数据的数据库化，也具备基础的管理端、用户端、审批流和 OAuth 能力。

但从题目要求来看，系统仍存在以下关键差距：

- 只完成了“数据库承载”，没有完成“从 CoPaw/OpenClaw 文件配置迁移到数据库”的业务闭环。
- “公共 / 部门 / 个人”三级模型没有完全统一为单一语义。
- 用户端当前更像“资源发现页”，而不是严格意义上的“当前用户可用资源列表”。
- 运行时权限拦截没有形成真正闭环，更多是列表过滤，不是执行时校验。
- 组织、部门、审批、授权之间仍有语义混用。

本计划的目标是分阶段完成以下事项：

1. 完成需求语义收口。
2. 补齐三级权限模型。
3. 完成管理控制台与用户端的能力对齐。
4. 完成运行时鉴权闭环。
5. 补文件配置迁移方案与导入能力。

---

## 2. 需求对齐结论

### 2.1 已实现

- Skill/MCP 主数据已入库。
- 用户、组织、资源申请、资源授权模型已存在。
- 管理台已支持资源增删改查与启停。
- 用户端已支持查看资源、申请部门资源。
- 审批端已支持通过、拒绝、撤销。

### 2.2 部分实现

- 三级权限已具备基础字段，但业务语义不完全一致。
- 部门管理员已存在，但其管理边界与用户组织边界没有完全统一。
- OAuth 已能发 code/token，但 consent、scope、revoke 仍不完整。

### 2.3 未实现

- 从文件配置自动迁移到数据库。
- 统一的运行时工具调用鉴权。
- 严格意义上的“当前可用资源列表”与“可发现资源列表”分离。
- 资源敏感字段在未授权时的展示收敛。

## 3. 总体实施原则

### 3.1 先收口语义，再改页面

不要先改 UI 文案或按钮交互，再回头修权限模型。应先定义清楚：

- 哪些资源是“可发现”的。
- 哪些资源是“可消费”的。
- 哪些资源需要审批。
- 授权事实由哪个表承载。

### 3.2 授权事实与申请流程分离

后续统一约定：

- `ResourceApplication` 只表示申请流程。
- `ResourceGrant` 只表示最终授权事实。

### 3.3 组织语义必须统一

统一定义：

- `organizationId`：用户所属组织，或资源归属组织。
- `departmentId`：部门管理员的管理范围。
- “部门级资源是否可用”不再由“同组织”直接决定，而由明确规则决定。

### 3.4 运行时鉴权必须以后端为准

前端页面只负责展示状态，真正的权限判断必须以后端执行入口为准，不能只依赖前端隐藏按钮。

## 4. 分阶段实施计划

## Phase 1：需求语义收口与数据模型补强

### 目标

统一“发现资源 / 可用资源 / 审批 / 授权 / 部门范围”的语义，避免继续在混合模型上叠加功能。

### 改动项

#### 4.1.1 明确接口职责

统一接口语义：

- `/api/client/skills`、`/api/client/mcps`
  - 定义为“资源发现接口”
  - 返回：公共资源 + 同部门可申请资源 + 自己的个人资源
  - 同时返回 `applicationStatus` 和 `grantStatus`

- `/api/v1/users/[id]/skills`、`/api/v1/users/[id]/mcps`
  - 定义为“用户当前可消费资源接口”
  - 返回：公共资源 + 自己的个人资源 + 已授权的部门资源

#### 4.1.2 固化三级权限语义

推荐统一为：

- 公共级
  - 所有人默认可用
  - 不需要单独申请
  - 仅超级管理员维护

- 部门级
  - 仅部门范围内用户可发现
  - 是否最终可用按授权策略决定
  - 由部门管理员或超级管理员维护

- 个人级
  - 仅资源 owner 可用
  - 由用户本人维护

#### 4.1.3 补数据库约束

建议在 Prisma schema 中增加或强化以下约束：

- `Skill.visibility` 与 `Mcp.visibility` 改成枚举。
- `Skill.sourceType` 与 `Mcp.sourceType` 改成枚举。
- 增加数据库级检查逻辑或应用级强校验：
  - `personal` 时 `ownerId` 必填
  - `company/department` 时 `organizationId` 必填
- `ResourceGrant` 增加“有效授权唯一”约束方案，避免出现同一用户对同一资源存在多条未撤销授权。

#### 4.1.4 统一组织与部门边界

需要作出明确决策：

方案 A，推荐：

- 用户 `organizationId` 为当前所在部门节点
- 部门资源 `organizationId` 为所属部门节点
- 部门管理员 `departmentId` 为可管理部门节点
- 后代节点继承通过 `path` 支撑

方案 B：

- 不使用层级继承，只做精确部门匹配

推荐采用方案 A，但必须一次性改清楚。

### 涉及文件

- `prisma/schema.prisma`
- `src/lib/resource-access.ts`
- `src/lib/organizations.ts`
- `src/app/api/client/skills/route.ts`
- `src/app/api/client/mcps/route.ts`
- `src/app/api/v1/users/[id]/skills/route.ts`
- `src/app/api/v1/users/[id]/mcps/route.ts`

### 验收标准

- 发现接口与消费接口语义清晰分离。
- 部门资源不会因为“同组织”直接被当成已可用资源。
- 授权状态只以 `ResourceGrant` 为准。
- Prisma migration 可正常执行。

## Phase 2：三级权限模型与审批授权主链路改造

### 目标

把当前“可见、申请、审批、授权、撤销”打成真正闭环。

### 改动项

#### 4.2.1 收紧部门资源使用逻辑

当前发现页可直接看到部门资源，这是合理的，但必须限制：

- 未授权时只能看到基础元信息
- 不能暴露敏感 `sourceValue`
- 页面上明确区分：
  - 可直接使用
  - 可申请
  - 待审批
  - 已拒绝
  - 已撤销

#### 4.2.2 统一审批通过逻辑

审批通过必须保证事务一致性：

- `ResourceApplication.status = approved`
- 创建或恢复 `ResourceGrant`
- 记录审批人
- 保证幂等

#### 4.2.3 统一审批拒绝逻辑

审批拒绝时：

- 只修改申请状态
- 不产生授权
- 支持后续重新申请

#### 4.2.4 补手工撤销与联动撤销

至少覆盖以下场景：

- 用户被停用时撤销全部有效授权
- 资源停用或删除时撤销关联授权
- 管理员手工撤销某个用户对某个资源的授权

#### 4.2.5 补授权状态视图

建议在管理端增加统一视图，支持：

- 看某个资源授权给了谁
- 看某个用户拥有哪些资源授权
- 从授权维度直接撤销

### 涉及文件

- `src/app/api/client/skills/[id]/apply/route.ts`
- `src/app/api/client/mcps/[id]/apply/route.ts`
- `src/app/api/admin/applications/route.ts`
- `src/app/api/admin/applications/[id]/approve/route.ts`
- `src/app/api/admin/applications/[id]/reject/route.ts`
- `src/app/api/admin/applications/[id]/revoke/route.ts`
- `src/app/(client)/client/page.tsx`
- `src/components/client/apply-button.tsx`

### 验收标准

- 用户申请通过后，消费接口立刻能看到资源。
- 用户被拒绝或被撤销后，消费接口立刻失效。
- 同一资源重复申请、重复审批不会产生脏数据。
- 用户端状态文案与后端真实状态一致。

## Phase 3：管理控制台能力补齐

### 目标

让管理台真正满足“增删改查、按三级分配、启用/禁用控制”的要求。

### 改动项

#### 4.3.1 资源管理页能力升级

在 Skill/MCP 管理页补齐：

- 按 visibility 筛选
- 按组织筛选
- 查看授权人数
- 查看申请人数
- 快速停用/启用

#### 4.3.2 增加资源授权管理入口

新增“授权管理”页或资源详情页授权面板，支持：

- 查看当前授权用户列表
- 查看待审批申请
- 给部门资源手动授权
- 手动撤销授权

#### 4.3.3 用户管理与部门管理员模型对齐

当前用户管理已有基础字段，但需要从产品能力上闭环：

- 超级管理员可创建/编辑部门管理员
- 部门管理员仅管理自己范围内资源和审批
- 普通用户不进入误导性的“资源管理页”

#### 4.3.4 公共级资源管理规则收口

明确公共级资源的维护责任：

- 仅超级管理员能创建、修改、删除公共资源
- 公共资源默认立即生效
- 公共资源不走申请流

## Phase 4：用户端与前台展示改造

### 目标

让用户界面严格符合题目中的“当前用户可用资源展示”和“部门级资源申请”要求。

### 改动项

#### 4.4.1 区分“可发现”与“可使用”

建议前台拆为两个视角：

- 我的可用资源
  - 展示当前真正可调用的资源
  - 数据来自消费接口

- 资源发现
  - 展示公共资源、可申请的部门资源、个人资源
  - 数据来自发现接口

如果暂时不拆页面，至少要在同一页面上视觉明确区分。

#### 4.4.2 未授权资源不显示敏感配置

未授权部门资源仅显示：

- 名称
- 标识符
- 描述
- 所属部门
- 当前申请状态

不要直接展示：

- `sourceValue`
- 实际调用地址
- 本地路径

#### 4.4.3 申请交互优化

优化前台状态：

- 未申请：显示“申请”
- 待审批：显示“待审批”
- 已拒绝：显示“重新申请”
- 已授权：显示“已可用”
- 已撤销：显示“已撤销，可重新申请”

#### 4.4.4 支持按分类汇总展示

展示逻辑对齐题目要求：

- 公共
- 所在部门
- 个人

同时明确“当前可用数”和“可申请数”。

### 涉及文件

- `src/app/(client)/client/page.tsx`
- `src/components/client/apply-button.tsx`
- `src/app/api/client/skills/route.ts`
- `src/app/api/client/mcps/route.ts`

### 验收标准

- 用户能一眼区分什么是可直接用、什么是需要申请。
- 未授权资源不再暴露敏感配置。
- 页面展示语义和后端数据语义一致。

## Phase 5：运行时鉴权闭环

### 目标

满足题目“AI 调用工具时自动校验权限，无权限返回友好提示”的要求。

### 改动项

#### 4.5.1 增加统一运行时资源解析层

新增统一服务层，例如：

- `src/lib/runtime-access.ts`

负责：

- 根据用户身份解析可调用资源
- 校验资源是否启用
- 校验是否有有效授权
- 返回标准化错误

#### 4.5.2 增加统一执行入口或代理入口

如果系统要真正服务 CoPaw/OpenClaw，需要提供统一接口，例如：

- `POST /api/runtime/skills/:id/invoke`
- `POST /api/runtime/mcps/:id/invoke`

在这里执行：

1. 认证
2. scope 校验
3. grant 校验
4. 资源可用性校验
5. 转发调用或返回友好错误

#### 4.5.3 统一错误码与提示

建议补以下标准错误：

- `FORBIDDEN_RESOURCE_NOT_GRANTED`
- `FORBIDDEN_RESOURCE_DISABLED`
- `FORBIDDEN_RESOURCE_SCOPE_REQUIRED`
- `NOT_FOUND_RESOURCE`

返回给上游时要友好可读。

#### 4.5.4 Bearer token 增加 scope 校验

当前 token 验证只校验是否合法，不校验 scope。需要新增：

- `requireScopes(['skills:read'])`
- `requireScopes(['mcps:read'])`
- `requireScopes(['skills:invoke'])`
- `requireScopes(['mcps:invoke'])`

### 涉及文件

- `src/middleware/api-auth.ts`
- `src/lib/oauth.ts`
- 新增 `src/lib/runtime-access.ts`
- 新增运行时调用路由

### 验收标准

- 无授权用户无法真正调用部门资源。
- 资源停用后调用立即失败。
- scope 不足时返回正确错误。
- 上游调用方能拿到明确可处理的错误信息。

## Phase 6：文件配置迁移与导入能力

### 目标

补齐题目最原始要求：将 CoPaw/OpenClaw 的 Skill/MCP 文件配置迁移到数据库。

### 改动项

#### 4.6.1 梳理现网文件格式

先确认：

- Skill 文件路径规则
- MCP 文件路径规则
- 配置字段结构
- 唯一标识生成规则
- 可见级别在文件中是否可推断

#### 4.6.2 设计导入器

新增导入脚本，例如：

- `scripts/import-skills.ts`
- `scripts/import-mcps.ts`

能力包括：

- 扫描目录
- 解析配置
- 去重
- 生成 identifier
- 映射 visibility / organization / owner
- 导入数据库

#### 4.6.3 提供一次性迁移模式

建议支持：

- `dry-run`
- `upsert`
- `report`

输出内容包括：

- 新增数量
- 更新数量
- 跳过数量
- 冲突项

#### 4.6.4 设计后续同步策略

两种方案二选一：

方案 A，推荐：

- 数据库作为唯一真源
- 文件仅做一次性导入，不再双向同步

方案 B：

- 文件与数据库长期双向同步

推荐方案 A，复杂度明显更低。

### 涉及文件

- 新增 `scripts/` 下导入脚本
- 可能新增 `docs/import-mapping.md`
- `prisma/seed.ts`

### 验收标准

- 可从既有 Skill/MCP 文件批量导入数据库。
- 导入支持重复执行且结果稳定。
- 导入报告能说明每条资源的处理结果。

## 7. 风险与注意事项

### 7.1 最大风险

- 组织语义改动后可能影响现有审批和页面过滤。
- 发现接口和消费接口拆分后，前端文案和数据源都要同步调整。
- 导入文件配置时，identifier 冲突需要提前定义规则。

### 7.2 兼容策略

建议使用灰度方式：

- 先保留旧接口语义，新增明确语义接口或加版本标记。
- 前端先接入新接口，再清理旧逻辑。
- 导入脚本先 dry-run，再执行真实导入。

### 7.3 不建议的做法

- 不要继续把 `ResourceApplication` 当最终权限事实来源。
- 不要在未定组织语义前就直接加更多前端逻辑。
- 不要在没有 runtime 校验前对外开放真正的调用入口。

## 9. 建议补充的测试用例

- 超级管理员创建公共资源后，普通用户立即可消费。
- 部门管理员创建部门资源后，本部门普通用户能发现但未授权前不能消费。
- 普通用户申请部门资源后，审批通过立即生效。
- 审批拒绝后用户不能消费，但可以重新申请。
- 授权撤销后消费接口立即失效。
- 资源停用后相关授权全部失效。
- 用户停用后相关授权全部失效。
- 无 scope 的 token 访问受限接口被拒绝。
- 无 grant 的 token 调用运行时执行接口被拒绝。
- 文件导入 dry-run 与真实导入结果一致。

## 10. 建议的实施结论

如果目标是尽快满足题目要求，推荐优先做以下最小闭环：

1. 收口发现接口与消费接口语义。
2. 收紧部门资源展示与授权逻辑。
3. 增加运行时统一鉴权入口。
4. 最后补文件导入器。

按这个顺序推进，改动风险最低，也最容易在每个阶段产出可验证结果。
